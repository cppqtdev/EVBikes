01

How C++ reaches QML

Before any individual class makes sense you need the mechanism. It is small, and once you have seen it you know where every other class plugs in.

Desktop Qt does this with Q_OBJECT, Q_PROPERTY, moc, qmlRegisterType and a QVariant round trip. Qt for MCUs throws all of it away. You write a plain struct, list its header in the .qmlproject, and a build tool writes the QML type for you. There is no registration call anywhere in your code.

Three steps, start to finish

// 1. a plain struct — no Q_OBJECT, no macros at all
#include <qul/property.h>
#include <qul/singleton.h>

struct VehicleData : public Qul::Singleton<VehicleData>
{
    Qul::Property<int>  speedKmh;
    Qul::Property<bool> absFault;
};
// 2. list the header — backend.qmlproject
Project {
    MCU.Module { uri: "ClusterBackend" }
    InterfaceFiles { files: [ "VehicleData.h" ] }
}
// 3. use it. no import of the type, no instantiation.
import ClusterBackend
Text { text: VehicleData.speedKmh + " km/h" }

And from C++, VehicleData::instance().speedKmh.setValue(52). The Text updates. You did not call anything on the UI.

The first thing to check, every time

A header that is not in InterfaceFiles is invisible to QML, however correct it looks. "The type does not exist" almost always means this.

The four building blocks

You wantUseChapter
A value QML can read and bind toQul::Property<T>3
One global object, reachable by nameQul::Singleton<T>2
Many instances, created in QMLQul::Object2
To tell QML "this just happened"Qul::Signal<T>4
The direction of travel

C++ pushes values in. QML pulls them out through bindings. You do not reach into QML to update the screen. If you want to, the answer is almost always a property you have not declared yet. The one exception is a signal, for things that are events rather than states.

Object and Singleton

Two classes, one decision: does your type exist once, or many times?

Qul::Singleton<T>Qul::Object
Headerqul/singleton.hqul/object.h
APIstatic T& instance()none — it is a marker
Instancesexactly oneas many as QML declares
Reached from QML asa name: VehicleData.speeda type you instantiate
Exported to QML aspragma SingletonQtObject
 
struct VehicleData : public Qul::Singleton<VehicleData>   // the type, twice. not a typo.
{
    Qul::Property<int> speedKmh;
};

That repetition is the Curiously Recurring Template Pattern — it is how the base knows what it is making a singleton of. The docs suggest a private constructor with the base as friend, so nobody creates a second one.

Qul::Object does not give you runtime creation

No heap means "many instances" still means a count fixed at build time — the objects QML declares, laid out statically. Reach for Qul::Object when QML genuinely owns the instances; otherwise Singleton serves you better. This project has ten singletons and no Qul::Object at all.

From this project — the split that matters

Ten singletons, one per subsystem: VehicleData, ConnectivityData, NavigationData, PhoneData, PhoneListData, SystemData, TripData, AlertData, ClusterInput, Simulator.

That split is the useful lesson, more than the API. One singleton per subsystem, named for what it holds. A page reads the singletons it needs and never talks to the bus.

03

Property

The one you will use most. In this project it appears 131 times; everything else combined appears twelve.

131Qul::Property
10Qul::Singleton
1Qul::Signal
1Qul::Timer

The complete API, and that is not a joke:

#include <qul/property.h>

Property()                        // zero-initialised
explicit Property(const T &value)
void setValue(const T &v)
const T &value()
const T &value() const

A plain int member is just a number. A Qul::Property<int> is a number the engine watches: call setValue and every binding that reads it is marked dirty and re-evaluated before the next frame. You write one line and never mention the elements that change.

Read with .value(), write with .setValue(). A property is not an int with extra powers; it is a box. Forgetting .value() is the most common compile error of week one.

One constraint from the docs

"Property type T that does not have built-in comparison operator must be provided with a user-defined operator==." The engine compares old and new to decide whether anything changed. Without one you get a compile error — the good outcome. The bad one would be a property that updates every frame forever.

The integer trap

QML has exactly one integer type. Properties of narrow types work, but a desktop bridge mirroring narrow types across the boundary corrupted every number on screen in this project: 8-bit and 32-bit survived, 16-bit did not.

The rule: narrow inside your own code, int at the QML boundary for anything in a signal signature. The comment in ClusterInput.h is the scar — "QML signal slots use its canonical int type; the hardware API stays byte-sized."

From this project

struct NavigationData : public Qul::Singleton<NavigationData>
{
    enum Maneuver : uint8_t { None = 0, Straight, SlightLeft, /* ... */ Destination };

    Qul::Property<bool>        active;
    Qul::Property<uint8_t>     maneuver;
    Qul::Property<uint32_t>    distanceToManeuverM;
    Qul::Property<uint16_t>    etaMinutes;
    Qul::Property<uint8_t>     laneMask;
    Qul::Property<std::string> roadName;
};

Three things to copy: the enum lives beside the property that uses it so QML writes NavigationData.SharpLeft and no screen knows that sharp left is 7; units are in the names so nobody divides by a thousand twice; and a bitfield is one property, not eight booleans — fewer properties means fewer bindings to re-evaluate.

Signal

A property says what is true. A signal says what just happened.

The thingIt is aUse
The speed is 52stateProperty
The rider pressed OKeventSignal
The battery is at 80%stateProperty
A text message arrivedeventSignal
The trip counter was reseteventSignal

The test: if you missed it, does it matter? A state you can read any time. An event you miss is gone. Model a button press as a boolean and you get a UI that drops fast double presses and occasionally latches on.

// ClusterInput.h                                from this project
struct ClusterInput : public Qul::Singleton<ClusterInput>
{
    enum Button : uint8_t { Up = 0, Down, Left, Right, Ok, Mode, Back };
    enum Action : uint8_t { Press = 0, LongPress };

    Qul::Signal<void(int button, int action)> buttonEvent;

    void inject(uint8_t button, uint8_t action);
};
Connections {
    target: ClusterInput
    onButtonEvent: {
        if (button === ClusterInput.Ok && action === ClusterInput.Press)
            Router.activate()
    }
}

Emit by calling it: buttonEvent(button, action). The whole input system here is one signal, and inject() is the seam — the real driver calls it from a GPIO handler, the desktop simulator from a keyboard event, and QML cannot tell.

Two traps

Unnamed parameters. Signal<void(int, int)> compiles, but the QML handler has nothing sensible to call them. The names you declare are the names in scope.

Emitting from an interrupt. Handlers run synchronously, which puts QML on the interrupt stack. Post to an EventQueue and emit from its onEvent instead.

05

Lists and models

For when you have several of something and QML needs to repeat over it.

Qul::ListModel — rows for a view

#include <qul/model.h>

virtual int count() const = 0;        // how many
virtual T data(int index) const = 0;  // the row
T get(int index) const;

Qul::Signal<void (int)> dataChanged;  // row `index` changed
Qul::Signal<void ()>    modelReset;   // the row COUNT changed

Two pure virtuals, two signals. The row struct's public fields become the roles QML reads as model.name, model.number.

Which signal matters. dataChanged(3) reloads one row and is cheap. modelReset() rebuilds the view and is not. Emit the cheap one whenever you can — and emit the expensive one whenever the count changes, or you see stale rows.

The constraint nobody warns you about

A Repeater's delegates are allocated at build time from a compile-time estimate. No heap means a row that appears at runtime has nowhere to come from. Keep the model constant and hide what you are not using:

Repeater {
    model: 8                                   // constant. always 8 delegates.
    ContactRow { visible: index < ContactModel.count }
}

The desktop build creates delegates on demand and will not warn you. The device froze.

Qul::ListProperty — a list as a property

#include <qul/listproperty.h>

void append(T *t);   T at(int index);   void clear();
int  count() const;  void removeLast(); void replace(int index, T newValue);
bool isStatic() const;  bool isDynamic() const;  bool isNull() const;
void setList(Qul::StaticList<T> *l);
void setList(Qul::DynamicList<T> *l);

Rule of thumb: if a Repeater or ListView consumes it, you want ListModel. If it is just "this object has several of those", you want ListProperty. And on a system with no heap, prefer a StaticList.

This project has neither — the contact list is a count property plus indexed accessor functions and a constant Repeater. Less elegant, completely predictable in memory, and it is why the UI does not freeze. For three to eight fixed rows, which is most of a cluster, the plain version wins.

EventQueue

The safe way to get data from an interrupt or another thread into the UI.

#include <qul/eventqueue.h>

template <typename EventType_,
          Qul::EventQueueOverrunPolicy overrunPolicy = EventQueueOverrunPolicy_Discard,
          size_t queueSize = 5>
class Qul::EventQueue

void postEvent(const EventType &event);
void postEventFromInterrupt(const EventType &event);
virtual void onEvent(const EventType &event) = 0;      // you implement this
virtual void onEventDiscarded(const EventType &event);
virtual void onQueueOverrun();
bool isOverrun() const;    void clearOverrun();        // since 2.3

A CAN frame arrives in an interrupt. You must not touch the UI there — the engine is not reentrant. So the interrupt does a memcpy and returns; the main loop picks it up and calls your onEvent, where writing properties is safe.

The default size of 5 is the trap

In this project eight CAN frames were posted per tick into a queue of five. Three were dropped every tick, silently, forever — and the desktop shim delivers synchronously, so the bug existed only on hardware and showed only as data that was quietly wrong.

Size it from your real rate: count the worst-case events between two drains — a drain is once per frame, so 16 ms at 60 fps — then double it. And override onQueueOverrun(), so a drop is a number you can see rather than data you cannot trust.

// src/backend/Backend.cpp                       from this project
class CanQueue : public Qul::EventQueue<evb::CanFrame,
                                        Qul::EventQueueOverrunPolicy_Discard, 16>
{
public:
    void onEvent(const evb::CanFrame &frame) override { g_decoder.decode(frame); }
};

class PhoneQueue : public Qul::EventQueue<PhoneChunk,
                                          Qul::EventQueueOverrunPolicy_Discard, 32>
{ /* ... */ };

Choosing the overrun policy

  • Discard for a stream where every item matters and losing a recent one is as bad as losing an old one — protocol chunks, keypresses.
  • Overwrite for a sampled value where only the latest matters — a sensor reading. Losing an old sample is free.

Interrupt and thread safety, exactly

On baremetal the DoubleQueue backend "is interrupt-safe as long as there is a single writer, because writes and reads are directed to different lists." Two interrupts posting to one queue is not safe without your own synchronisation. With threads or an RTOS the queue is thread-safe through mutexes or RTOS queues. Draining is safe to interrupt either way.

When NOT to use it

An EventQueue is for crossing a boundary, not a general message bus. If both ends are already on the main loop, call the function — a queue adds a frame of latency, a fixed buffer that can overflow, and a POD restriction, in exchange for nothing. Events are memcpy'd, so a std::string in an event compiles and then corrupts.

Timer

Run something later, or every N milliseconds.

#include <qul/timer.h>

Timer(int interval = 0);          virtual ~Timer() override;   // destructor STOPS it
void setInterval(int msec);       int  interval() const;
void setSingleShot(bool s);       bool isSingleShot() const;
void start();  void start(int msec);  void stop();  bool isActive() const;
template <typename FuncArg> void onTimeout(const FuncArg &f);

Four behaviours from the docs, each of which has bitten somebody

  • It does not start by itself. Constructing with an interval does not start it.
  • "Setting the interval of an active timer does not change the next event." The current countdown finishes on the old interval.
  • "Only the last callback stays active." Calling onTimeout() twice replaces; it does not add.
  • The destructor stops it. Which is why a timer must be a member, never a local.
Always clamp the elapsed time

Your callback computes "how long since last time" and advances something by that much. The first tick after startup, after a long frame, or after a debugger pause can be enormous.

const uint32_t gap     = nowMs - m_lastTickMs;
const uint32_t elapsed = gap > kMaxTickMs ? kMaxTickMs : gap;

And watch for unsigned wraparound in that subtraction. Here a timestamp one millisecond ahead of the comparison time wrapped to four billion and every node was declared dead, several times a second.

One timer can drive several rates. This project runs a single 16 ms timer and accumulates m_pollElapsedMs and m_clockElapsedMs, acting when each passes its own threshold — a 16 ms animation, a 200 ms poll and a 1000 ms clock from one timer. Three timers would cost three times the bookkeeping for nothing.

Application and startup

Four classes own the beginning and end of your program.

// src/main.cpp                                  from this project
int main()
{
    Qul::initHardware();          // 1. clocks, pins, peripherals
    Qul::initPlatform();          // 2. display, framebuffer, input
    Backend::init();              // 3. your own setup

    Qul::Application app;         // 4. constructing it initialises QUL
    static struct ::Main item;    // 5. root item, STATICALLY
    app.setRootItem(&item);       // 6. hand it over

    Backend::startRuntime();      // 7. your timers and queues
    app.exec();                   // 8. the frame loop, forever
    Backend::stopRuntime();
    return 0;
}

The order is not negotiable. If you get a blank screen, walk this list — this project added a boot trace that prints before each step, because the last line printed names the call that did not return.

Main is generated from Main.qml by qmltocpp; a pointer to it converts to Qul::RootItem *, which is the only thing RootItem is for. Note static — it must outlive exec(), and on an MCU the stack is the scarcest memory you have.

The application does not take ownership of any of them. Keep them alive yourself — in practice, file-scope statics.

Getting 96 KB of VRAM back

The text cache defaults to 192 KB. With the static font engine the glyphs are already in flash, so the cache only holds text that changes — on a cluster, a handful of readouts.

#include <qul/application.h>        // same header. there is no applicationconfiguration.h

Qul::ApplicationConfiguration config;
config.setTextCacheSize(96 * 1024);
Qul::Application app(config);         // passed to the CONSTRUCTOR, not set statically
A warning worth the space

Inventing the header name qul/applicationconfiguration.h stopped this project's build outright. The class lives in qul/application.h and has existed since Qt Quick Ultralite 2.1. Check the real header before you include it — thirty seconds of grep against hours of a failed build round.

Qul::ApplicationSettings (since 2.0) is reached through the application, and its documented property is the UI language: app.settings().uiLanguage.setValue("pl_PL"). If you ship more than one language, that is the switch.

An image provider, start to finish

struct CameraProvider : public Qul::ImageProvider
{
    Qul::SharedImage requestImage(const char *uri, size_t uriLength) override
    {
        if (uriLength == 4 && memcmp(uri, "live", 4) == 0)
            return cameraImage;        // Image converts implicitly to SharedImage
        return Qul::SharedImage();     // falsy: nothing to draw
    }
};

static CameraProvider g_cameraProvider;                      // static: no ownership taken
Qul::Application::addImageProvider("camera", &g_cameraProvider);
Image { source: "image://camera/live" }

The provider id is the host part, and the uri you receive is everything after it — "live", not the whole string.

When you edit pixels that are already on screen, bracket it. The guard does beginWrite()/endWrite() with RAII so you cannot forget the second half:

{
    Qul::ImageWriteGuard guard(cameraImage);
    memcpy(cameraImage.bits(), newFrame, frameSize);
}   // endWrite() happens here, even on an early return
PaintedItemDelegate — rarely, and that is the point 
virtual Rect boundingRect(Size size) const = 0;
virtual void paint(DrawingDevice *device, const Rect &clip,
                   const Transform &transform, Size size,
                   float opacity) const = 0;
void update();  void update(int x, int y, int width, int height);

Pairs with the PaintedItem QML type. Reach for it when the thing genuinely cannot be images and QML items — a waveform, a live plot. A paint() runs on the CPU every dirty frame; an image is a blit. This project draws its gauges as pre-rendered layers for exactly that reason and has no painted items at all.

Resources and files

Bytes you shipped in flash, and filesystems Qt did not know it had.

#include <qul/binaryresource.h>

BinaryResource(const char *uri);
const uchar *data() const;   size_t size() const;   size_t alignment() const;
Project { BinaryFiles { files: [ "data/lookup_table.bin" ] } }

The data is already in flash, mapped, addressable. data() is a pointer to it — no read, no copy, no buffer. Perfect for calibration tables, lookup curves, audio samples. Check alignment() before casting the pointer to a struct; flash does not care, your CPU does.

For a few hundred bytes a static const uint8_t[] is simpler. BinaryResource wins when the data is big, tool-generated, or should be swappable without recompiling — a 200 KB table as a C array is a miserable compile.

Where the bytes areUse

Note the division of labour: images you ship are decoded at build time by qulrcc and stored ready to draw. An ImageDecoder is only for pixels that show up while the program runs. And ResourceStorageSectionInfo's two version pairs — application and resource — exist so an over-the-air update can ship new art without reflashing the application.

String, Status, Flags

Three small types. Each solves one problem, and each has a sharp edge.

Qul::String — qul/unicodestring.h

"Designed as an interface type. Its main use case is as a function parameter type." One function that accepts a literal, a std::string or a buffer, with no overload for each.

It does not own the data

The UTF-8 constructor creates "a view on a UTF-8 string". Treat it like std::string_view: fine as a parameter, dangerous as a return value or a stored member.

Qul::String makeLabel() {
    char buf[32]; formatInto(buf);
    return Qul::String(buf);        // buf dies here. the String points at it.
}

For storage use std::string in the property, as this project does: Qul::Property<std::string> roadName;. The std::string constructors need QUL_STD_STRING_SUPPORT defined in the core library — if they do not compile, that is why.

Qul::Status<ErrorEnum> — since 2.10

Success or a typed error code, without exceptions and without a bare return -1 the caller has to decode. hasError(), error(), setError(), clearError(), and operator bool() which is true on success — the opposite of an integer return code. Mixing the two conventions in one codebase is how you ship an inverted check.

Qul::Flags<Enum> — since 2.12

A bitmask the compiler checks: testFlag, setFlag, toUnderlyingType, and the bitwise operators. New in 2.12; on 2.11 and earlier you write the bit twiddling by hand, which is what this project does with a single uint32_t telltaleFlags property. That is worth noting on its own — one flags property is cheaper than sixteen booleans, because it is one value for the engine to track.

Confirm these two headers yourself

The reference shows module-style includes — <Status> and <Flags> — rather than a path, and Qul::String is qul/unicodestring.h, which is not what most people would guess. Check your own installation before you include:

grep -rln "class Status\|class Flags" ~/QtForMCU/QtMCUs/*/include/qul/

Location and maps

Three classes feed QtPositioning and QtLocation. Both are marked experimental.

ClassYou implementRegistered withQML consumer
GeoPositionInfo— (a data carrier)——
GeoPositionSourcegetCurrentPosition()registerGeoPositionSource()PositionSource
MapTileFetchergetTileImage()addMapTileFetcher()Map

Note the shape: the engine pulls from you. Your job is to answer "where are we right now" quickly from whatever your GNSS driver last parsed — not to block on a serial port inside a call that runs on the main loop.

GeoPositionInfo's hasLatitude(), hasDirection() and hasSpeed() matter: a GPS with a weak lock gives a position but no heading, and a stationary one gives no meaningful speed. Check before you use, or the compass needle points north every time the signal dips. speed and timestamp only exist from 2.12.

Do the tile arithmetic before you start

A map is the most expensive thing an MCU cluster can draw. A 256×256 tile at 4 bytes per pixel is 256 KB decoded, per tile, and a 1280×480 screen wants fifteen or more to cover it.

This project draws navigation as pre-rendered turn arrows and route images, not live tiles, precisely because that arithmetic did not work. A turn arrow is a few KB. If your need is "which way do I turn", pre-rendered art is cheaper and clearer.

Putting it together

The shape a working backend takes, and why each layer exists.

The rule worth more than any class here

Pages never touch the bus; decoders never touch QML. The decoder is a pure transformation from bytes to properties, so you can unit test it on a host with no board. Bit packing is miserable to debug on hardware and trivial to test off it.

The eight habits

  1. One singleton per subsystem, named for what it holds.
  2. Units in property names — distanceToManeuverM, etaMinutes.
  3. Enums beside the properties that use them, so QML never writes a bare number.
  4. Widen to int at the QML boundary. Narrow inside your own code.
  5. Size every EventQueue from your real data rate and override onQueueOverrun.
  6. Clamp elapsed time in every timer callback.
  7. Decoders never touch QML; pages never touch the bus.
  8. Verify the header before you include it. Guessing has cost this project a build round already.
