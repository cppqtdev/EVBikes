# CYT4DN cluster: implementation and hardware readiness

Target selected: Infineon TRAVEO T2G 6M / CYT4DN. Current design: 1280 × 480.
This is a desktop-verified prototype with a board resource profile, not a certified production cluster.

## Implemented

- Settings uses one Router index for fixed menu slots and separate page loaders. Both chevrons and neighbouring titles accept clicks; keyboard left/right uses the same route.
- Three permanent speed digit cells, fixed alignment and baseline, fixed unit label. Hundreds hide without moving the other cells. Two digits remain visible below 100.
- Trip shows tenths; speed, trip, odometer, range, fuel and warning flags originate in project CAN frames.
- Simulator preserves fractional distance between 50 ms updates. Previously integer truncation discarded sub-metre travel, freezing trip and turn distances.
- Repeatable 90-second city speed cycle includes acceleration, braking, stops and restarting. Sport targets exceed 100 km/h. Demo energy consumption drives SOC/range.
- Route distance retains fractional travel and advances through six maneuver segments. Navigation uses the existing phone transport, not an invented OEM CAN navigation mapping. The map is schematic guidance, not a GPS road map.
- CAN controls left/right/hazard blink phase. QML no longer adds a second independent blink cycle.
- Sixteen additional EV/ICE/common telltales; independent powertrain freshness displays “Warning data unavailable” after missing frames. Telltale applicability depends on powertrain type.
- Connections page supports explicit demo-phone disconnect/re-pair while stopped, including clearing/restoring navigation and lists. Hardware Bluetooth and Wi-Fi are unavailable until a radio driver is supplied.
- Ride-mode selection reaches the UI through simulator CAN frames. It does not directly overwrite VehicleData.
- New simulation counters and payloads use fixed-width types. `uint64_t` is used only for distance multiplication to prevent intermediate overflow. QML `int`, API-required integers and existing signed signal containers are not blindly narrowed.

Keyboard: M cycles City, Sport, Low Tyre, Overheat, Crash, Lamp Test, Petrol Demo. P requests park. Left/right select the bottom dock; Enter activates it. Settings → Connections contains pairing controls.

## Memory arithmetic

Framebuffer bytes = width × height × bytes per pixel × buffer count. These figures exclude pitch alignment, command buffers, glyphs, objects, stacks and resources.

| 1280 × 480 | One full buffer | Two full buffers |
|---|---:|---:|
| 16 bpp | 1,228,800 B / 1.172 MiB | 2,457,600 B / 2.344 MiB |
| 24 bpp | 1,843,200 B / 1.758 MiB | 3,686,400 B / 3.516 MiB |
| 32 bpp | 2,457,600 B / 2.344 MiB | 4,915,200 B / 4.688 MiB |

Qt lists CYT4DN with 640 KiB SRAM and 4 MiB VRAM. A conventional double 32-bpp framebuffer exceeds VRAM before any other allocation. Do not put this framebuffer in internal SRAM.

The TRAVEO port builds at 32 bpp; lower layer depth is selected with `ItemLayer.depth`, not by changing `QUL_COLOR_DEPTH` to 16. The port supports on-the-fly rendering with a circular line buffer instead of two complete frames. A 1280 × 64 × 4 line buffer is 327,680 bytes; command buffers and other allocations are additional. This is an example calculation, not a measured allocation for this project.

`profiles/traveo/` is generated by `tools/sync_project_files.py` and selected by CMake for `tviic2d*` platforms. It uses:

- External-flash resource storage (`QulResourceDataInExternalFlash`).
- No resource/glyph caching, avoiding the desktop 21 MiB decompression-cache configuration.
- Alpha8 for suitable monochrome masks; hardware lossless compression for coloured resources.
- The platform's default rendering setup. No unmeasured custom line/command buffer tuning is imposed.

The board export requires Infineon ResourceGenerator for RLE. The installed exporter reached resource conversion but stopped because ResourceGenerator was missing. A linked target build, actual display resolution, linker-map audit and peak VRAM measurement remain required. NoCaching may increase flash bandwidth; measure frame time and display underruns before choosing final settings.

## Asset results

`python3 tools/audit_assets.py` reports every PNG directly referenced by QML. Its decoded estimate uses one byte/pixel for verified Alpha8 masks and four for colour. It is an upper-bound pixel-storage estimate, not peak runtime memory or final RLE flash size.

| Referenced assets | Before shell trimming | After |
|---|---:|---:|
| PNG file bytes | 890,067 | 846,031 |
| Estimated decoded bytes | 19,123,667 | 15,776,456 |

Fourteen shell layers had full-screen transparent margins. Cropping them saves **3,347,211 decoded bytes (3.19 MiB)** without rescaling artwork. Original sources are retained. Run `tools/trim_shell_assets.py` after regenerating the shell, then `tools/sync_project_files.py`.

PNG is an authoring format, not a guarantee of low runtime RAM. Keep icons at their actual display size; use Alpha8 tintable masks, avoid duplicate resources, reduce large transparent overlays and measure QUL's generated assets. Loading all 15 MiB of estimated decoded pixels into 4 MiB VRAM is not viable. External resource storage, rendering mode and cache policy must be considered together.

## CAN / radio integration still needed

The IDs in `src/core/can/CanIds.h` are the project's **demo protocol**, not a CYT4DN or motorcycle standard. Supply the actual bike DBC/signal table before connecting to a vehicle.

Additional demo frame `0x103`, classic CAN DLC 4, little endian:

| Field | Encoding |
|---|---|
| Byte 0 | 0 = EV, 1 = petrol |
| Byte 1 | Fuel percent, 0..100 |
| Bytes 2..3 | Warning mask |

Mask bits 0..15: engine fault, oil pressure, engine temperature, low fuel, EFI, service, motor fault, motor temperature, battery temperature, charging fault, reduced power, brake warning, traction control, cruise, immobilizer, charging. Invalid DLC/type/fuel is rejected. This frame has a 500 ms freshness deadline. Demo lamp frames carry the instantaneous blink phase; a bike whose CAN carries indicator *commands* needs a different adapter.

`src/platform/board/PlatformBoard.cpp` remains a bring-up template. Required: actual CAN pins/transceiver, nominal/data bit rates, vendor SDK initialization and RX callbacks, bus-off recovery, queue overflow diagnostics, radio UART/SPI transport and backlight driver. No vehicle-control commands are implemented.

CYT4DN selection alone does not supply a BLE/Wi-Fi radio, firmware, SSID scanner or network stack. The Connections UI exposes only the simulator capabilities. Pairing hardware needs the chosen module and its protocol. Existing demo PIN/profile enrollment logic is not production authentication; automatic simulated scan completion is disabled outside the simulator.

The petrol scenario demonstrates warning decoding; it is not a complete petrol dashboard. Existing battery/motor instruments remain EV instruments. Production ICE support needs fuel/range/engine signal mapping and the corresponding gauge configuration.

## Verification and remaining gates

- QUL 2.12.2 desktop Debug build succeeds.
- Core tests and backend smoke pass with AddressSanitizer, UndefinedBehaviorSanitizer and LeakSanitizer outside the sandbox's ptrace restriction.
- Tests cover fractional distance, malformed powertrain frames, timeout/recovery, ten simulated minutes of distance/range, parking and phone disconnect/re-pair/list restoration.
- Actual QUL window reaches ride, updates speed and maneuver distance; shell cropping and three-digit speed were visually inspected. Settings pages changed after keyboard/click input, with the selected title matching page content after replacing PathView and the shared dynamic loader.
- Host tests do not establish embedded leak freedom or worst-case execution time. Final gates: target linker map, heap/stack high-water marks, long hardware soak, CAN overload/bus-off/unplug, power-cycle storage, display underruns and interaction latency.
- SDK-generated assembly still produces a GNU-stack linker warning on desktop.

## Other boards

Share protocol/decoder/backend code, but use separate board/display/resource profiles. A 1280 × 480 asset set cannot be promised on every board in the supplied PDFs. Smaller SRAM targets need native-resolution layouts, fewer overlays and partial buffering where their port supports it. VRAM-equipped boards need their own layer policies; external SDRAM boards need measured bus bandwidth/cache placement. Do not treat resizing a framebuffer as a complete port.
